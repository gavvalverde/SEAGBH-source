# Firebase RTDB — auditoria de autorização e integração local

Escopo da [issue #70](https://github.com/gavvalverde/SEAGBH-source/issues/70). O inventário começou na `main` em `bcd08aa` e no [PR #69 em `fba5dc2`](https://github.com/gavvalverde/SEAGBH-source/pull/69/files). Os PRs #79 e #80 integram a infraestrutura do emulador à `main`. O #69 foi integrado e valida a UID administrativa no Gerenciamento de Clientes. O [registro de evidências da #70](firebase-issue-70-evidencias.md) distingue essa entrega da liberação operacional ainda pendente.

A política informada pelo operador exige uma única UID administrativa para escritas no RTDB. Configure `SEAGBH_FIREBASE_ADMIN_UID` com a UID autorizada, no ambiente do processo ou no `.env` local. Variáveis do processo têm precedência, inclusive quando vazias. A ferramenta compara a UID exata antes de abrir a janela ou ler o histórico e exige a mesma UID na renovação. O RTDB aplica a autorização de escrita a partir do token do Firebase.

A [fixture por UID](../tests/integration/firebase/rules.uid.fixture.json) reproduz as regras fornecidas pelo operador com uma conta fictícia. A leitura individual da licença é pública. O RTDB autoriza a escrita pela UID, valida o ID e os campos na gravação de dados e ignora as validações ao remover um nó com `null`. A [fixture por claim](../tests/integration/firebase/rules.fixture.json) continua sendo um controle independente de atomicidade. Consulte a [matriz de homologação](firebase-homologacao.md) e o procedimento de coleta em leitura para conferir a aplicação da política na instância operacional.

## Matriz de operações

O Gerenciamento envia o ID token na query `auth` para o RTDB. Os dois consumidores instalados usam GET sem token. A matriz relaciona as chamadas encontradas no código com a política informada.

| Operação | Ator e autenticação atual | Autorização informada | Dependência e efeito de negar | Evidência no código |
| --- | --- | --- | --- | --- |
| GET `licenses/{id}` | Aplicativo instalado sem token. Gerenciamento com ID token para cache e restauração | Leitura individual legada dos campos estritamente necessários. Restringir a listagem e dados privados | Clientes instalados usam a resposta para revogação, renovação e alertas. Erro HTTP entra em tolerância offline de 72 h, sem atualizar a última verificação. HTTP 200 com `null` é exclusão e bloqueia imediatamente. O #69 interrompe a restauração diante de erro | [Licenciamento](../src/core/licenca.py), [Gerenciamento no #69](https://github.com/gavvalverde/SEAGBH-source/blob/fba5dc22dd63d7675a2a9505db19b545994911ce/tools/gerador_chaves.py) |
| PUT `licenses/{id}/auto_renew` | Gerenciamento com ID token | Papel administrativo | Emissão e alternância de renovação dependem da escrita. O cliente instalado só lê o estado e pode expirar com o estado anterior | `_on_gerar` cria o nó pela primeira escrita do filho. `_on_toggle_auto_renew` só atualiza o cache após confirmação |
| PUT `licenses/{id}` | Gerenciamento com ID token na restauração | Papel administrativo | Sem recriação no RTDB o cliente ainda recebe `null` e continua bloqueado. O #69 preserva o arquivo morto em caso de recusa | `_restaurar` consulta primeiro. Após `null`, recria os campos básicos antes de atualizar o histórico |
| PUT/DELETE `licenses/{id}/revoked_at` | Gerenciamento com ID token | Papel administrativo | Sem escrita, a revogação ou reativação anterior permanece. O cliente usa a data para o prazo de regularização de 24 h | `_on_revogar` grava a data e `_on_reativar` remove o campo. `_consultar_firebase` interpreta a data |
| PUT `licenses/{id}/alerts_muted_until` e `.../expiry_override` | Gerenciamento com ID token | Papel administrativo | Alerta e vencimento continuam com os valores anteriores. Clientes dependem da leitura desses campos | `_on_mute_alerts` e `_on_edit_expiry` confirmam a escrita antes de atualizar o cache |
| DELETE `licenses/{id}` e `revoked/{id}` antes do #69 (histórico) | Gerenciamento com ID token | Papel administrativo nos dois caminhos | Um cliente pode ver a licença excluída enquanto o nó auxiliar permanece | A base histórica usava dois DELETE sequenciais. A leitura legada continua em `licenses/{id}` |
| PATCH `/.json` com `licenses/{id}` e `revoked/{id}` na `main` após o #69 | Gerenciamento com ID token | Papel administrativo nos dois caminhos. Preservar a recusa de escrita geral na raiz | Recusa de qualquer caminho impede a exclusão. Em timeout, o estado remoto pode ser desconhecido. O #69 preserva o histórico local até confirmação | `_excluir_licenca_remota_atomicamente` envia um PATCH com dois caminhos relativos e valor `null` |
| GET, PUT, PATCH ou DELETE direto em `revoked/{id}` | O código inspecionado só remove o nó auxiliar na exclusão. Demais métodos aparecem na fixture | GET negado a todos. Escrita pela UID administrativa | Nenhum consumidor atual foi localizado para esse nó. A exclusão do #69 depende da permissão de escrita nele, inclusive para alvo ausente | Revogação corrente reside em `licenses/{id}/revoked_at` |
| GET `updates/latest` | Atualizador instalado sem token | Leitura pública do registro de versão | Sem a leitura, o atualizador deixa de informar a publicação, inclusive quando marcada como obrigatória | [Atualizador](../src/core/atualizacao.py) retorna `None` em erro HTTP ou resposta incompatível |
| PUT `updates/latest` | Gerenciamento com ID token | UID administrativa | A versão publicada anterior permanece. Uma permissão ampla nesse nó permite alterar metadados que apontam para o executável | `_on_publicar_atualizacao` confirma o PUT antes de informar sucesso |

## Execução e resultados

Requisitos da execução verificada: Python **3.12.10**, Firebase CLI **15.35.0**, Java Temurin **21.0.13.1** e RTDB Emulator **4.11.2**. O Firebase CLI pode baixar o JAR oficial no primeiro uso. Na raiz do repositório, execute:

```sh
python -B tests/integration/firebase/run.py
```

Para um Firebase CLI portátil, passe `--firebase CAMINHO` ao mesmo comando e disponibilize Java no PATH do processo. O lançador copia apenas as fixtures e o teste para uma pasta temporária, usa configuração de CLI isolada e seleciona exclusivamente o projeto `demo-seagbh-authz`. Auth e RTDB escutam em loopback, nas portas 19199 e 19200. O teste exige os endereços e o projeto esperados, usa REST direto sem proxies e inicia cada caso com os dados sintéticos previstos. O token de administração da infraestrutura do emulador é usado somente para preparar as contas e os dados e para observar o estado sem o filtro das regras. As operações sob teste usam ID tokens emitidos pelo Auth local ou são anônimas. [Firebase Local Emulator Suite](https://firebase.google.com/docs/emulator-suite/connect_rtdb)

- **11 testes de integração aprovados.** Leitura legada de licença e atualização, recusa de listagem, recusa de escrita anônima e comum, token inválido, restrição de sessão expirada na fixture, atribuição protegida de claim, operações administrativas e PATCH com ou sem registro auxiliar foram exercitados no emulador de Auth e RTDB.
- **Atomicidade observada.** Com ambos os caminhos permitidos, o PATCH removeu os dois alvos e preservou os vizinhos. Bloqueando `licenses/{id}` e depois `revoked/{id}`, o emulador devolveu `Permission denied` e a leitura posterior confirmou que ambos os registros e os vizinhos ficaram intactos. Um DELETE de controle confirmou que o outro caminho continuava individualmente permitido em cada caso. A documentação define atualização multilocal como uma operação em que todas as escritas têm sucesso ou todas falham. [PATCH REST](https://firebase.google.com/docs/database/rest/save-data) · [Atomicidade](https://firebase.google.com/docs/database/web/read-and-write#update_specific_fields)
- **Expiração no emulador.** Na primeira execução, com a regra checando apenas o papel, o token emulado vencido recebeu HTTP 200 e gravou a mudança. A fixture final inclui uma condição explícita `auth.token.exp * 1000 > now` para testar a recusa por prazo. Os três grupos de escrita negaram o token e o estado permaneceu igual. O resultado caracteriza esses emuladores e a fixture. [Auth Emulator 15.35.0](https://github.com/firebase/firebase-tools/blob/v15.35.0/src/emulator/auth/operations.ts) · [Variáveis das regras RTDB](https://firebase.google.com/docs/reference/security/database/)
- **Regressões offline em Python 3.12.10.** 98 testes de licenciamento e 24 subtestes aprovados na `main` com pytest 9.2.0 do cache local. Os 33 testes de Auth do HEAD do #69 passaram em checkout temporário com PyQt6 real offscreen. Houve zero tentativas de conexão nas duas suítes offline. Os checks de Auth do #69 também terminaram com sucesso em Windows e Ubuntu. [CI do #69](https://github.com/gavvalverde/SEAGBH-source/actions/runs/45072404227)

## Proposta de autorização e transição

1. **Inventariar as regras reais em modo leitura.** Um operador autorizado confere permissões e herança a partir da raiz, provedor e origem dos papéis, campos de cada nó e versões distribuídas. Registre só quais operações são permitidas, quais papéis existem e quais consumidores foram confirmados. A concessão em um nó ancestral se propaga aos filhos. A auditoria deve confirmar em particular se uma conta comum pode escrever em licenças, revogações ou atualizações. [Sintaxe e herança das regras](https://firebase.google.com/docs/database/security/core-syntax)
2. **Separar login de acesso administrativo.** Para um único administrador, a regra de escrita usa `auth.uid`. A configuração local deve corresponder à mesma conta. Revise ambas em uma troca de administrador. O controle de escrita permanece no RTDB, inclusive em cada caminho do PATCH. Uma política de revogação imediata de sessões exigiria validação separada. [Condições RTDB](https://firebase.google.com/docs/database/security/rules-conditions) · [Revogação de sessões](https://firebase.google.com/docs/auth/admin/manage-sessions)
3. **Manter os contratos instalados.** Preserve a consulta individual anônima ao conjunto mínimo de campos que controla a licença e o GET anônimo de `updates/latest`. Primeiro audite se os nós hoje contêm dados privados. O GET de um nó retorna o conteúdo daquele nó. Mova dados administrativos para área privada ou para um backend em etapa planejada. A regra de listagem deve ser avaliada separadamente da regra por ID e o ID de licença nunca deve funcionar como credencial. Valide um cliente de cada versão distribuída com fixtures representativas, incluindo `200 null`, recusa HTTP, prazo de revogação e notificação de atualização.
4. **Controlar o histórico e a emissão local separadamente.** O controle remoto não protege o histórico JSON e as chaves no disco do operador, inclusive em máquinas compartilhadas. Confirme propriedade e permissões do armazenamento e avalie emissão por serviço confiável. A migração futura da assinatura HMAC embarcada deve emitir somente via backend, preservar validação das licenças vigentes durante a transição e definir uma janela de rollback com versão legada compatível e política de assinatura conhecida. Valide a origem de atualizações separadamente do papel que publica metadados.
5. **Liberar em etapas.** Guarde a revisão aprovada das regras em armazenamento restrito e use um ambiente de homologação com dados sanitizados. A reposição dos dados de teste e as regressões devem ser repetíveis. Antes da promoção, aprove o plano com o responsável e defina rollback para uma versão de regras revisada que preserve as duas leituras legadas. Se esses GETs começarem a falhar ou o PATCH administrativo for negado, suspenda a promoção e restaure a versão aprovada. Qualquer exceção que reabra escrita administrativa exige decisão humana explícita. Mudanças em regras, contas, claims e dados de produção permanecem fora desta etapa.

## Classificação e decisão sobre o #69

| Pendência | Classificação | Evidência |
| --- | --- | --- |
| Sessão de conta comum abrindo o Gerenciamento ou lendo os históricos | **Corrigida no #69** | Login e renovação exigem a UID configurada. A janela e as funções de persistência revalidam a sessão administrativa |
| Necessidade das duas leituras sem token | **Comprovada no código e na fixture** | Os consumidores legados não fornecem token. Os testes preservam a leitura individual e distinguem ausência de recusa |
| PATCH com HTTP 200 e exclusão parcial por recusa de regra | **Refutada no contrato testado** | A recusa real no emulador conservou ambos os alvos em ambos os sentidos. Isso não resolve a incerteza de um timeout |
| Segunda ação substituir a retomada da primeira ou iniciar outra renovação | **Refutada no caminho testado** | No #69 a guarda retorna antes de alterar a ação pendente, a janela fica desabilitada e o teste aciona a guarda novamente, mede uma renovação e uma retomada. O conforto do feedback de espera é uma questão de UX ainda não verificada em uso real |
| Escrita por conta comum ou exposição de dados em produção | **Ainda não verificada** | Regras implantadas, conteúdo real e contas não foram consultados nesta missão |
| Compatibilidade do PATCH com as regras implantadas e dos GETs com todas as versões distribuídas | **Ainda não verificada** | Suítes offline e emulador exercitam o HTTP sob regras de fixture, não as permissões do ambiente operacional |

O #69 já foi integrado ao código. A liberação operacional não se presume: depende de confirmar por leitura a instância e as regras vigentes, configurar a UID no perfil autorizado e verificar a exposição dos arquivos locais. Consulte as condições na [homologação](firebase-homologacao.md).
